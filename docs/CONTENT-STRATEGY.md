# Taitung.md 內容策略：什麼是真的、什麼不能假的、內容從哪來

> 這份文件定義了 Taitung.md 的內容紅線、資料來源策略、分類系統、以及社群協作機制。

---

## 一、絕對不能用 AI 生成的東西

這是最重要的一章。Taitung.md 的可信度建立在「這裡的每一個字都有來源」。以下是完整的禁止清單：

### 🚫 絕對禁止 AI 生成

| 類型 | 為什麼不行 | 會造成什麼問題 |
|------|-----------|---------------|
| **口述歷史 / 引言** | 這是真人說的話，捏造等於偽造證詞 | 被引用的人或其家人會發現，信任永久崩塌 |
| **人物故事 / 人物描述** | 描述真人的經歷，錯一個細節就是對人的不尊重 | 法律風險 + 社群反感 |
| **統計數據 / 數字** | 「海岸線後退 23%」這種數據如果是假的，整個學術聲道就廢了 | 被學術社群打臉，永遠失去公信力 |
| **原住民文化描述** | 族語翻譯、祭儀描述、文化意涵——錯了就是文化冒犯 | 部落社群抵制，最嚴重的後果 |
| **地名 / 歷史事件 / 年代** | 「都蘭部落可追溯至數百年前」——如果不確定就不要寫 | 地方文史工作者會第一時間指出錯誤 |
| **引用來源 / 參考文獻** | 捏造一個不存在的論文或書籍 | 被查證後信任歸零 |
| **照片描述 / 圖說** | 如果說「這是 2024 年都蘭海岸」但其實不是 | 跟假新聞無異 |
| **田野筆記** | 如果沒有人真的去過那個地方 | 整個「田野」聲道變成小說創作 |
| **音檔逐字稿** | 如果沒有對應的音檔 | 偽造口述歷史紀錄 |
| **社群回答 / 讀者投稿** | 捏造「匿名 · 台東市 · 3 小時前」 | 社群參與全部變成假的，根基崩塌 |

### ⚠️ AI 可以輔助但必須人工審核

| 類型 | AI 可以做什麼 | 人必須做什麼 |
|------|-------------|-------------|
| **文章結構 / 大綱** | 根據真實資料整理架構 | 確認每一段都有對應來源 |
| **資料摘要** | 把長篇論文濃縮成段落 | 確認摘要沒有歪曲原意 |
| **翻譯（中↔英）** | 初稿翻譯 | 母語者或專業譯者審核 |
| **SEO / meta description** | 生成初稿 | 確認沒有誇大或失實 |
| **排版 / 視覺呈現建議** | 建議版面配置 | 不涉及內容真假問題 |

### ✅ AI 可以自由做的事

- 程式碼（前端、後端、資料處理腳本）
- 設計系統（色彩、字型、排版規則）
- UI/UX 原型
- 資料庫結構設計
- 爬蟲腳本（爬取公開資料）
- 內容格式轉換（把政府 CSV 轉成網站可用的 JSON）

## 二、內容從哪裡來：真實資料來源

### 原則：每一句話都要能回答「這是從哪裡來的」

Taitung.md 的內容有三種來源，每一種都必須標註：

```
📊 公開資料（政府、學術、機構）→ 爬取 + 整理 + 標註來源
👤 社群貢獻（真人寫的、錄的、拍的）→ 投稿 + 審核 + 標註作者
📰 公開報導（新聞、紀錄片、書籍）→ 引用 + 標註出處 + 不全文轉載
```

### A. 可程式化爬取的公開資料

這些是已經確認存在的台東相關公開資料源，可以寫腳本定期抓取：

**政府開放資料（data.gov.tw）**
- 台東觀光景點資料集（dataset #7777）— JSON，含座標、描述
- 台東觀光活動資料集（dataset #7778）— JSON
- 台東餐飲資料集（dataset #7779）
- 台東住宿資料集（dataset #7780）
- 台東縣統計年報 — 人口、產業、土地利用
- 用途：提供景點基礎資訊、座標、分類——這是骨架

**中央氣象署 API（opendata.cwa.gov.tw）**
- 台東即時天氣、氣溫、降雨
- 用途：首頁「此刻的台東」可以顯示真實天氣，不是假資料
- 需要免費申請 API key

**國家文化記憶庫 API（memory.culture.tw）**
- 台東相關文化素材（照片、文物、文獻）
- 有 RESTful API，JSON 格式
- 用途：提供真實的歷史照片和文化資料

**文化部文化資產（nchdb.boch.gov.tw）**
- 台東古蹟、歷史建築、文化景觀、傳統藝術、民俗
- 台東有 47 處歷史建築、5 處古蹟、3 處文化景觀
- 用途：「時間」地景層的核心資料

**水利署開放資料（data.wra.gov.tw）**
- 卑南溪流域水位、降雨
- 用途：環境資料、河川相關故事的背景數據

**林業署台東分署（taitung.forest.gov.tw）**
- 關山、延平、台東、大武、成功五個事業區
- 用途：「土地」地景層的森林資料

**OpenStreetMap（osm.tw）**
- 台東完整地理資料，ODbL 授權
- 用途：地圖底圖、POI 資料

### B. 需要人工整理的公開資料

**台東大學研究**
- 南島文化研究中心的公開出版物
- 理工學院環境相關研究
- 用途：「知識」地景層的學術聲道來源

**中研院資料（srda.sinica.edu.tw / data.ascdc.tw）**
- 調查研究資料庫（SRDA）— 社會、經濟、人口調查
- 數位文化中心 — 人類學、歷史、藝術素材
- 用途：學術研究的引用來源

**台灣歷史地名查詢（twstudy.iis.sinica.edu.tw）**
- 台東各地的歷史地名、沿革
- 用途：每篇文章的地名考據

**東管處（eastcoast-nsa.gov.tw）**
- 海岸環境監測、觀光資訊
- 用途：海岸環境相關故事的數據來源

## 三、分類系統：重新想過

你說得對——12 個地景層的想法沒有錯，但它變成了「分類頁面」就死了。重新想一下分類的用途：

### 分類不是導航，是濾鏡

使用者不應該「選一個分類 → 看列表」。分類應該是：

1. **後台標籤**：每篇內容標記所屬層級（可多重標記），用於搜尋和推薦
2. **地圖濾鏡**：在地圖上切換不同層級的內容顯示
3. **故事串聯**：同一個地點的不同層級故事自動串在一起

### 真正的導航方式

使用者進入網站後，找到內容的方式應該是：

```
路徑 1：首頁滾動 → 被一篇故事吸引 → 點進去 → 透過「相關故事」繼續
路徑 2：地圖探索 → zoom 到一個區域 → 看到那裡的故事浮現 → 點擊
路徑 3：本週提問 → 看別人的回答 → 被某個回答引到一篇正式故事
路徑 4：搜尋 → 直接找
```

沒有一條路徑是「選分類 → 看列表」。

### 12 層保留但改變角色

| 層 | 在後台 | 在前台 |
|----|-------|-------|
| 土地 🗺️ | 標籤 | 地圖上的地理特徵圖層 |
| 時間 🏛️ | 標籤 | 時間軸上的事件 |
| 人群 👥 | 標籤 | 故事的主角類型 |
| 知識 🎓 | 標籤 | 學術聲道內容 |
| 生活 🍚 | 標籤 | 日常觀察類故事 |
| 慶典 🎭 | 標籤 | 季節 + 行事曆連動 |
| 體驗 🏄 | 標籤 | 可以去做的事 |
| 青年 🌱 | 標籤 | 年輕人的聲音 |
| 設計 🎨 | 標籤 | 空間/視覺相關 |
| 教育 📚 | 標籤 | 學校/學習相關 |
| 永續 🌿 | 標籤 | 環境/保育相關 |
| 連結 🚂 | 標籤 | 交通/對外關係 |

前台不會有「12 個格子讓你選」，但你在看一篇故事的時候，會在底部看到「這篇故事屬於：土地 · 人群 · 生活」，點擊任何一個標籤可以看到相關的其他故事。

## 四、社群協作：故事和資訊為主，聲音為輔

### 修正方向

之前太偏向「聲音」了。現實是：大部分人不會為一個網站去錄音。但大部分人**願意打幾行字回答一個有趣的問題**。

### 協作方式的優先順序

```
最容易（最多人會做）
  ↓
  1. 回答每週提問（打字 < 200 字）
  2. 對現有故事留言補充（「我知道這件事，補充一下⋯⋯」）
  3. 提交一個線索（「嘿，XXX 地方有個 XXX 的故事，值得去了解」）
  4. 寫一段個人經驗（300-800 字的短文）
  5. 上傳照片 + 一句圖說
  6. 提交完整文章 / 田野筆記
  7. 上傳音檔 / 影片
  ↓
最難（最少人會做）
```

### 「鉤子」設計

**鉤子 1：每週提問**（門檻最低）
- 每週一個跟台東有關的問題
- 只要打字回答，不用帳號（但可以選擇留名或匿名）
- 所有回答即時可見
- 優秀回答被策展進正式故事裡（附作者名）
- 問題本身就是內容——問題的選擇反映編輯觀點

**鉤子 2：補充現有故事**（中低門檻）
- 每篇故事底部有「你知道更多嗎？」的區塊
- 不是留言板——是結構化的補充：
  - 「我可以補充一個事實」
  - 「我有相關的個人經歷」
  - 「這裡有一個錯誤需要修正」
  - 「我有這個地方的照片」
- 補充內容經過審核後會被整合進故事本體（標注貢獻者）

**鉤子 3：線索投遞**（低門檻，高價值）
- 「台東有一個值得被記錄的故事」
- 只需要提供：地點 + 一兩句描述 + 為什麼值得記錄
- 編輯團隊從線索池裡挑選，做成正式故事
- 線索提供者在故事裡被致謝

**鉤子 4：開放資料協作**（技術門檻，但價值最高）
- GitHub PR 模式
- 幫忙把政府 CSV 轉成可用格式
- 幫忙查證一篇故事裡的數據
- 幫忙翻譯（中↔英，或族語標注）

## 五、AI 在這個網站裡的正確角色

AI 不寫內容，AI 做基礎建設：

### AI 可以做的事

```
1. 爬取 + 清洗公開資料
   - 定期從 data.gov.tw 抓取台東資料集
   - 把政府格式的 CSV/XML 轉成網站用的 JSON
   - 比對新舊資料，標記更新

2. 輔助結構化
   - 幫投稿者的文字加上 frontmatter（地點、標籤、座標）
   - 建議「這篇文章跟哪些現有故事相關」
   - 自動從文章內容提取關鍵字和座標

3. 品質檢查
   - 檢查引用的 URL 是否還活著
   - 檢查數據是否跟公開來源一致
   - 標記「這段內容超過一年沒更新」

4. 翻譯初稿
   - 中文 → 英文的初步翻譯（需人工審核）

5. 搜尋 + 推薦
   - 語意搜尋
   - 「讀完這篇可能也想看」推薦
```

### AI 絕對不做的事

```
❌ 不寫任何會出現在網站上、以「內容」形式呈現的文字
❌ 不生成假的統計數據
❌ 不生成假的引言或口述歷史
❌ 不生成假的社群回答
❌ 不生成假的照片描述
❌ 不以任何形式冒充真人的聲音
```

## 六、內容標注規範

每一篇內容都必須在前端清楚標注來源類型：

```yaml
# 在 frontmatter 中
source_type: public-data | community | news-reference | academic | field-research
source_details:
  - type: government-opendata
    name: "交通部觀光署台東觀光景點資料集"
    url: "https://data.gov.tw/dataset/7777"
    accessed: 2026-04-10
  - type: community-contribution
    author: "林清源"
    verified: true
    reviewer: "台東大學南島文化研究中心"
  - type: academic
    citation: "劉益昌等，《東海岸阿美族聚落空間研究》，中研院民族所，2018"
ai_generated: false  # 必填欄位
ai_assisted:         # 如果 AI 有參與，說明參與了什麼
  - "翻譯初稿（已由人工審核）"
  - "資料格式轉換"
```

在前端，每篇文章底部都會顯示：

```
📎 資料來源：交通部觀光署開放資料 · 中研院民族所
👤 社群貢獻：林清源（口述歷史）· 陳柏翰（田野筆記）
🤖 AI 輔助：翻譯初稿、資料格式轉換
```

## 七、內容生命週期

```
線索投遞 → 編輯評估 → 資料收集（爬取公開資料 + 邀請社群補充）
    → 初稿撰寫（基於真實資料）→ 事實查核 → 上線
    → 社群補充 → 持續更新 → 定期標記「最後更新日期」
```

每篇文章的狀態：
- 🌱 **種子**：只有線索，還沒有完整內容
- 🌿 **生長中**：有基礎資料，邀請社群補充
- 🌳 **成熟**：經過查核，內容完整
- 🍂 **需更新**：超過一年沒更新，數據可能過時

這個狀態會在文章頂部標示，讓讀者知道這篇內容的可信度。
