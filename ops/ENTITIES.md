# ENTITIES — 實體解析紀律（反混淆）

> **這份文件處理自動化研究最致命的失敗模式：把不同的事情混成一件。**
>
> 抓不到資料只是效率問題，下次再抓。把「都蘭部落」和「都蘭村」混成一個，會讓整個資料庫的每一則相關陳述都變成錯的，而且**看起來完全正常**——這種錯誤不會報錯，只會安靜地腐蝕全部產出。

版本：v1.0 ｜ 制定：2026-08-06 ｜ 上位文件：`METHOD.md`

## 一、根本原則

### P1. 名稱不是識別

**永遠不要用名稱當 key。** 名稱是實體的一個屬性，不是它的身份。

```yaml
# ❌ 錯：名稱當 key，「都蘭」會吸走五個不同東西的資料
都蘭:
  介紹: "阿美族部落，也是東河鄉的一個村，山上有遺址..."

# ✅ 對：每個實體有自己的 ID，名稱只是屬性
- id: settlement.dulan-atolan
  type: settlement
  names: { zh: "都蘭部落", amis: "'Atolan", ja: "都巒社" }
- id: admin.donghe-dulan-village
  type: administrative-division
  names: { zh: "都蘭村" }
  parent: admin.donghe-township
```

### P2. 三態，不是二元（Fellegi-Sunter）

**v1.1 修訂**：原設計只有「合併／不合併」。文獻回顧發現這是錯的——記錄連結的標準框架 Fellegi-Sunter 對每組配對取**三種**動作：

```
link  |  possible-link  |  not-link
                ↑
        中間態是一等公民，不是暫時狀態
```

最佳連結程序的目標是：**在控制兩類條件錯誤率的前提下，最小化 possible-link 的數量**——注意是「最小化」不是「消滅」。硬把中間態逼成二選一，正是製造混淆的來源。

→ `possible-link` 對應本專案的 `disambiguation_status: unresolved`（§4），**它是合法的長期狀態**，可以永遠停在那裡而不影響系統運作。

### P2b. 預設不合併（Default to Split）

**兩個看起來一樣的東西，預設當成兩個實體，除非有證據證明是同一個。**

這跟一般 AI 的直覺相反。LLM 天生傾向「這兩個講的應該是同一件事吧」，因為那讓敘述更流暢。**流暢是這裡的敵人。**

合併的成本 = 汙染所有相關陳述，且極難察覺。
分裂的成本 = 兩筆記錄，之後發現同一個再合併即可。

**成本不對稱 → 預設分裂。**

### P3. 合併必須是明示的、有證據的、可撤銷的

```yaml
- id: settlement.dulan-atolan
  merged_from: [tmp.dulan-tribe-a, tmp.atolan-village]
  merge_evidence:
    - source: "臺東縣政府原住民族行政處部落名冊 2024"
      note: "明列 'Atolan 之漢字為都蘭部落"
  merged_at: 2026-08-06
  merged_by: agent            # agent | human
  reversible: true
```

`merged_by: agent` 的合併在月度回顧時要抽查。連 `merge_evidence` 都沒有的合併 → CI 直接 fail。

### P4. 斷言綁在實體 ID 與來源上，不綁在名稱上

每一則事實（claim）的結構：

```yaml
- claim_id: c-00417
  subject: settlement.dulan-atolan      # 綁 ID，不綁「都蘭」
  predicate: population
  object: { value: 1240, unit: person }
  temporal: { as_of: 2024-12-31 }        # ← 幾乎所有錯誤都源於漏掉這個
  source: src-0233
  confidence: attested
```

### P5. 不做跨來源摘要

**這是最容易被忽略、卻最常製造混淆的操作。**

當 AI 讀了 5 篇關於都蘭的文章然後「摘要一段」，它會把 5 個來源、可能來自 5 個不同年份、談 5 個不同子主題的陳述，融成一段讀起來很順的文字。**融合的那一刻，來源歸屬就永久遺失了，而且沒有任何方法可以事後還原。**

**這條原本只是直覺，文獻回顧後有了實證依據**（`LITERATURE.md` §2.1）：

> 「產出越多引用的模型，必須從越多檢索段落聚合資訊，因而**提高跨來源事實誤植與混淆（misattribution or conflation of facts across sources）的機率**。」
> —— *Cited but Not Verified: Parsing and Evaluating Source Attribution in LLM Deep Research Agents*（[arXiv:2605.06635](https://arxiv.org/html/2605.06635v1)）

另有大規模實證：2025 一年估計 **146,932+** 筆幻覺引用進入學術文獻，且**到 2025 年底仍在上升未見平緩**，即便 RAG 與推理模型持續進步（[arXiv:2605.07723](https://arxiv.org/pdf/2605.07723)）。

**推論**：既然「聚合越多來源 → 混淆機率越高」是已觀察到的機制，降低混淆的直接手段就是**不聚合**。

規則：
- ✅ 單一來源內的摘要 —— 可以，摘要仍綁定該來源
- ❌ 跨來源的融合式摘要 —— 禁止
- ✅ 跨來源的**並列** —— 可以，且這正是 `docs/RETHINK.md` 想要的「對話式多聲道」
- ✅ **自產引用必須做存在性驗證**（URL 存活 + 標題比對），不能只檢查格式正確。格式正確的幻覺引用是最危險的一種

> 這裡有個漂亮的巧合：反混淆的技術要求（來源必須並列不得融合），和 v2 設計上想要的敘事效果（四種聲音在同一頁對話），**指向同一個實作**。倫理約束和設計目標在這裡是同一件事。

### P6. 對齊既有權威檔，不自建（v1.1 新增）

**原設計打算自建地名 registry。那是重複造輪子，而且會造出比既有權威更差的輪子。**

台灣已有成熟的權威檔，本專案的 registry 只負責兩件事：**（一）本地 ID ↔ 外部權威 ID 的對映；（二）權威檔涵蓋不到的實體**（當代團體、活動、計畫）。

| 實體類型 | 權威檔 |
|---|---|
| 地名（含歷史更名） | 中研院 [臺灣歷史文化地圖 THCTS](https://gis.rchss.sinica.edu.tw/thcts/) — 含臺灣地區地名查詢系統，分荷西／明鄭／清／日治／戰後各期圖層，**直接對應 §2.2 的歷史更名問題** |
| 地圖底圖 | [臺灣百年歷史地圖](https://gis.rchss.sinica.edu.tw/twhgis/)（有 [WMTS 服務](https://gis.sinica.edu.tw/tileserver/)，可直接接進網站） |
| 部落 | 原民會[核定部落名冊](https://www.cip.gov.tw/zh-tw/news/data-list/7CDD0E527E32B424/index.html)（最新版 2018-04-17 刊登公報）＋ [data.gov.tw dataset 7094](https://data.gov.tw/dataset/7094) 部落 GIS 點位 |
| 文化資源 | 中研院 [CRGIS](https://crgis.rchss.sinica.edu.tw/) |
| 國際對接 | Wikidata QID（選填欄位 `wikidata_qid`） |
| 文化遺產本體 | CIDOC CRM（**不全面採用**，但 entity `type` 詞彙表須能對映其 class，保留互通性） |
| 出處 metadata | W3C PROV-O 的 Entity / Activity / Agent 三元 |

> **原民會核定部落名冊直接解決 §2.4 的「部落 ≠ 行政區」層級混淆**——它是官方認定的部落實體清單，與行政區劃是兩套獨立的 ID 空間。

## 二、台東的實際陷阱清單

這不是理論範例，這是這個題材真實存在的坑。每一條都要進 registry 當測試案例。

### 2.1 一名多實體（同名不同物）

| 名稱 | 實際上是幾個不同實體 |
|---|---|
| **都蘭** | 都蘭部落（阿美族聚落）／都蘭村（東河鄉行政區）／都蘭山／都蘭遺址／都蘭糖廠（今藝文空間） |
| **卑南** | 卑南族（族群）／卑南鄉（行政區）／卑南遺址（考古）／卑南溪／卑南社（歷史聚落）／**清代「卑南」曾泛指今台東市一帶** |
| **知本** | 知本部落（卑南族，Katratripulr／卡大地布）／知本溫泉區／知本溪／知本國家森林遊樂區 |
| **長濱** | 長濱鄉（行政區）／**長濱文化（舊石器時代考古文化，八仙洞）** ← 兩者層次完全不同，混淆會很難看 |
| **大武** | 大武鄉（台東）／大武山（屏東台東交界，**不在大武鄉**）／大武部落 |
| **太麻里** | 太麻里鄉／太麻里溪／太麻里部落 |
| **成功** | 成功鎮／成功漁港／成功商水 |

### 2.2 歷史更名（時間軸上的同一實體，不同名）

這類是**反向風險**：應該合併卻被當成兩個。

| 舊名 | 今名 | 注意 |
|---|---|---|
| 火燒島 | 綠島鄉 | |
| 紅頭嶼 | 蘭嶼鄉 | |
| 新港 | 成功鎮 | 「新港」全台多處撞名，跨縣市檢索必須加限定 |
| 里壠／里壟 | 關山鎮 | |
| 台東廳 | 台東縣 | 行政層級與轄域**都改過**，統計數字不可直接跨期比較 |

### 2.3 命名政治（不可擅自統一）

| 情況 | 處理 |
|---|---|
| 達悟族 / 雅美族 | 涉及自稱與他稱的爭議。**兩個名稱都保留為別名，不擅自選定「正確」的那個**，並在 entity 上標 `naming_contested: true` 附說明 |
| 部落族語名 vs 漢字名 | 兩者都是正名，不是「翻譯」。族語名優先，漢字名並列 |
| 台東 / 臺東 | 同一實體，`臺` 為正式用字。**檢索時兩者都要查**，否則會漏掉大量文獻 |

### 2.4 層級混淆（最常見的量化錯誤）

| 陷阱 | 例子 |
|---|---|
| 縣 vs 鄉鎮 vs 村里 vs 部落 | 「台東的阿美族人口」——縣的數字被寫成某部落的 |
| 部落 ≠ 行政區 | 一個部落可能跨兩個村；一個村可能有三個部落 |
| 計畫 vs 執行單位 vs 補助單位 | 「XX 計畫由 YY 執行」常被寫成「YY 的計畫」 |
| 統計年度 vs 發布年度 | 2026 年發布的 2024 年統計，被寫成「2026 年台東有…」 |

**規則：任何量化陳述必須同時綁 `spatial_level`（county／township／village／settlement）與 `temporal.as_of`。缺任一 → CI fail。**

## 三、可執行檢查

| # | 規則 | 檢查方式 |
|---|---|---|
| N1 | 每個 entity 必須有 `id`、`type`、`names`，`id` 全域唯一 | ✅ 機器 |
| N2 | entity `id` 必須符合 `{type}.{slug}` 格式 | ✅ 機器 |
| N3 | 任何 claim 的 `subject` 必須是已註冊的 entity `id`，不得是自由文字 | ✅ 機器 |
| N4 | 量化 claim 必須有 `temporal.as_of` 與 `spatial_level` | ✅ 機器 |
| N5 | `merged_from` 存在時必須有 `merge_evidence` | ✅ 機器 |
| N6 | 陷阱清單（§2.1）中的名稱出現在內容裡時，必須已消歧義（連到具體 entity id） | ✅ 機器 |
| N7 | 同名不同 id 的 entity 存在時，內容中該名稱**單獨出現**（無限定詞）→ 警告 | ✅ 機器 |
| N8 | 偵測到跨來源融合摘要的徵兆（一段文字掛 >1 個 source 且無並列結構）→ 警告 | ✅ 機器（啟發式） |
| N9 | 歷史更名對照表中的舊名出現時，必須連到同一 entity 並標注該名稱的有效年代 | ✅ 機器 |
| N10 | `naming_contested: true` 的實體，內容中不得只用單一名稱 | ✅ 機器 |

## 四、當無法判斷是一個還是兩個

依 P2，**預設分裂**，並且：

1. 兩個都建 entity，各自標 `disambiguation_status: unresolved`
2. 互相加 `possibly_same_as: [other-id]`
3. 寫進 `BACKLOG.md`，標 `needs-disambiguation`
4. 在 JOURNAL 記錄：為什麼無法判斷、需要什麼證據才能判斷

**「需要什麼證據才能判斷」這一句是重點。** 它讓下一輪執行（或人類）知道該去查什麼，而不是重新面對同一團迷霧。
